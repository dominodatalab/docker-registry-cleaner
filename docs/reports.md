# Analysis Commands

## Report JSON schema

Every report generated by `image_size_report`, `user_size_report`, and the
deletion-analysis commands (`delete_archived_tags`, `delete_unused_environments`,
`delete_old_revisions`, `integrity_check`, `delete_image`'s deletion-analysis
report) now includes a standardized shape alongside its existing,
report-specific fields:

```json
{
  "schema_version": 2,
  "summary": {
    "count": 12,
    "total_size_bytes": 104857600,
    "total_size_gb": 0.1,
    "...report-specific summary fields, unchanged..."
  },
  "entries": [
    {
      "tag": "507f1f77bcf86cd799439011-3",
      "size_bytes": 8738133,
      "...report-specific fields, unchanged..."
    }
  ],
  "...this report's existing top-level fields, unchanged..."
}
```

- `entries` is always a flat list, and every entry carries `tag` — even
  for reports that previously grouped by ObjectId
  (`unused-environments.json`, `old-revisions.json`), nested per user
  (`user_size_report.json`), or split into two lists by status
  (`deletion-analysis.json`). `null` for `tag` is expected on
  `integrity-check.json`, whose issues are mostly about referential
  problems with no image to point to.
- `summary.count`/`total_size_bytes`/`total_size_gb` are computed
  identically for every report (`len(entries)`, `sum(size_bytes)`) — a
  **naive** sum, not dedup-aware. Where a report already had a
  dedup-aware total under the same names (`delete_old_revisions.py`
  only), that field was renamed to `total_freed_size_bytes`/
  `total_freed_size_gb` rather than silently redefined; every other
  report's pre-existing size fields already meant the same naive sum, so
  nothing needed renaming there.
- **Additive, not a replacement.** Every field this tool has ever
  documented in this file — `grouped_by_object_id`, `grouped_by_parent`,
  `archived_tags`, `unused_images`/`used_images`, `users[].images`, the
  `docker_tag`/`image_tag` field names, and everything else — is still
  present, unchanged, alongside the fields above. Nothing reading the
  previously-documented shape needs to change.

This is phase 1 of a larger standardization; see
[`report-schema-standardization-plan.md`](report-schema-standardization-plan.md)
for the full rationale, the remaining phases, and which internal
consumers (`report.html`, `python/api.py`'s Prometheus metrics reader) do
and don't need to change as a result — as of this phase, neither does,
since both already read fields this change never touches.

## reports

Generates usage reports by querying MongoDB for image usage across runs, workspaces, models, projects, scheduled jobs, organizations, and app versions.

```bash
docker-registry-cleaner reports
```

Reports are saved to the `reports/` directory. They are also auto-generated by deletion commands when missing, so you rarely need to run this manually unless you want to pre-generate or refresh them.

---

## image_size_report

Generates a report of the largest Docker images sorted by total size, showing the space that would be freed if each image were deleted (accounting for shared layers).

```bash
docker-registry-cleaner image_size_report
```

Output is saved to `reports/` and printed to the console.

---

## user_size_report

Generates a report of registry space usage grouped by the user who created each environment revision, showing who is consuming the most storage.

```bash
docker-registry-cleaner user_size_report
```

---

## health_check

Verifies connectivity to all required services before running deletions.

```bash
docker-registry-cleaner health_check
```

Checks:
- Docker registry connectivity
- MongoDB connectivity
- Kubernetes access (if applicable)
- S3 access (if configured)

Deletion scripts automatically run health checks before operations. Run this manually to diagnose connection issues.

---

## run_registry_gc

Runs Docker registry garbage collection inside the registry pod to reclaim storage after image deletions.

```bash
docker-registry-cleaner run_registry_gc
```

Only applicable for internal (in-cluster) Docker registries. For external registries (ECR, ACR, etc.), garbage collection is managed by the registry service itself.

Garbage collection is also triggered automatically when deletion commands are run with `--run-registry-gc`.

---

## reset_default_environments

Unsets default environments for users and organizations:
- Clears `userPreferences.defaultEnvironmentId`
- Clears `organizations.defaultV2EnvironmentId`

```bash
docker-registry-cleaner reset_default_environments
```

This is a MongoDB-only command. Use it to remove stale default environment references before running cleanup operations.
